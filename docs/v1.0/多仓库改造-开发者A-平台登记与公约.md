# 多仓库改造任务书 A：平台登记与研究基线公约

**负责人：** 开发者 A（平台核心方向）

**建议分支：** `feature/research-registry`

**PR 目标：** `develop`
**前置条件：** 本任务开始前，从最新 `develop` 新建分支；不要合并或依赖 `feature/component-download`。

## 1. 任务目标

将当前平台内 `research/` 的职责逐步调整为“项目内算法源码目录”，同时在平台核心建立不依赖数据库的**研究基线公约与算法登记中心**。平台能够展示研究方向、公共实验规则、已登记算法方案及其兼容条件，但不保存或下载外部算法仓库的实际源码。

本任务对应未来架构中的 A 层：`AI_TT_PLATFORM` 同时承担平台公共能力和研究基线公约。算法源码由独立 C 类仓库维护，本任务不创建、克隆或删除这些仓库。

## 2. 范围与边界

### 2.1 本任务必须完成

1. 新增项目内、受 Git 管理的登记目录，建议结构如下：

   ```text
   research-registry/
   ├─ registry.yaml
   ├─ directions/
   │  ├─ small-object.yaml
   │  └─ knowledge-distillation.yaml
   ├─ algorithms/
   │  └─ <algorithm-id>.yaml
   └─ conventions/
      ├─ dataset-format.md
      ├─ evaluation-metrics.md
      ├─ engine-compatibility.md
      ├─ algorithm-package-spec.md
      └─ release-and-reproducibility.md
   ```

2. 建立后端只读接口，读取、校验并返回登记信息；不得把算法/模板定义迁移到数据库。
3. 在前端新增“研究基线公约”入口或页面，展示：
   - 研究方向；
   - 数据格式、评测指标和引擎兼容性规则；
   - 已登记算法的名称、状态、引擎、数据格式、最低平台版本和仓库地址；
   - 缺少登记文件、字段错误或读取失败时的明确提示。
4. 为现有“小目标检测”和“知识蒸馏”创建方向登记；为当前已存在的基线/改进方案创建**元信息登记**。登记不代表算法已经迁移或实际可运行，状态必须如实标为 `draft`、`review` 或 `published`。
5. 补充单元测试/接口测试和相关文档。

### 2.2 本任务明确不做

- 不新建外部 GitHub 算法仓库。
- 不修改统一 Runner 的训练分流、启动、停止和日志读取逻辑。
- 不把后台 Git sparse checkout、克隆、删除目录作为正式算法安装机制。
- 不删除当前 `research/`，不批量移动已有算法文件。
- 不改变平台现有四级用户角色的定义。
- 不启动、关闭或重启后端、Runner。

## 3. 双方共同接口约定

本约定由开发者 A 维护，开发者 B 的试点算法必须遵守。字段可以在 PR 审查中增补，但不得自行破坏兼容性。

每个算法登记至少包含：

```yaml
schema_version: 1
id: small-object/yolo11-baseline
name: YOLO11 小目标检测基线
direction: small-object
status: draft
repository:
  url: https://github.com/<organization>/AI_TT_ALGO_SMALL_OBJECT_YOLO11_BASELINE.git
  default_ref: develop
  stable_ref: null
platform:
  min_version: null
engine:
  id: ultralytics
  version: 8.4.115
data_format: yolo
algorithm_manifest: algorithm.yaml
description: 说明该方案的定位、边界与当前验证状态。
```

规则：

- `id` 全局唯一，格式为 `方向/方案简称`；仅小写字母、数字和连字符。
- `repository.url` 仅用于展示、登记和后续受控接入；当前阶段不能由浏览器或后端直接把任意 URL 交给 Git 执行。
- `stable_ref` 应优先填写 Release Tag 或完整提交；未形成稳定版本可为空。
- `engine.id` 当前只允许 `mmdet`、`ultralytics`、`custom`、`paper`；其中 `paper` 仍不可运行。
- 路径、入口、参数等不接受绝对路径、盘符和 `..`。
- 算法元信息对拥有平台仓库读取权限的成员可见；算法源码的读取权限由独立算法仓库控制。

## 4. 阶段性目标与完成程度

每个阶段结束时都应提交一个可审查的本地提交。未达到该阶段的“完成标志”时，不要提前开始下一阶段，也不要在 PR 中写为“已接入”。

### 阶段 A0：协议冻结

**要做什么：** 阅读 `README.md`、`docs/v1.0/技术说明文档.md`、`docs/v1.0/GitHub协作流程.md`、`docs/v1.0/算法集成规范.md`；提交登记 YAML 的字段说明、方向样例和算法登记样例。

**完成标志：** 开发者 B 能拿到一份确定的 `id`、引擎、版本、数据格式、仓库地址和状态字段清单，并确认自己的试点 `algorithm.yaml` 应如何填写。

**尚未完成时不能声称：** 不得称“平台已支持外部算法仓库”或“算法已接入训练”。本阶段只有协议和样例，没有运行能力。

### 阶段 A1：登记文件与校验服务

**要做什么：** 建立 `research-registry/` 目录、后端 Registry Service 和只读接口。服务端固定读取项目内的登记目录，校验 YAML、ID 唯一性、方向/引擎/数据格式和相对路径规则。

**完成标志：** 通过接口可返回两个方向和现有算法的登记信息；目录不存在、YAML 无效、字段缺失、未知引擎、重复 ID 都会返回明确原因；测试覆盖这些失败场景。

**尚未完成时不能声称：** 文件能被读取不等于登记有效；不能只把 YAML 原文直接透传给前端而不做服务端校验。

### 阶段 A2：研究基线公约页面

**要做什么：** 增加前端 API 封装和独立的“研究基线公约”页面，展示方向、公约文档入口、算法登记、兼容条件和实际状态。

**完成标志：** 正常、空列表、后端错误和无效字段时均有清晰页面状态；算法显示 `draft/review/published` 的真实含义，不把草稿误标为可训练。

**尚未完成时不能声称：** 页面能显示算法名称不等于用户已经拥有该算法的源码或训练权限。

### 阶段 A3：旧目录兼容与文档收口

**要做什么：** 填写现有小目标检测、知识蒸馏及当前基线/改进包的登记；保持旧 `research/` 机制可用；更新使用、技术和算法接入文档。

**完成标志：** 现有训练页、数据集和结果功能没有回归；文档明确“项目内旧目录仍是过渡机制”“登记不代表源码已迁移”。

**尚未完成时不能声称：** 不得删除、移动或宣布废弃旧 `research/` 目录；算法迁移要等开发者 B 的试点验证完成。

## 5. 验收标准

- [ ] 平台启动后无需数据库中的算法模板记录，也能读取研究基线公约与算法登记。
- [ ] 前端能正确显示两个方向和已登记算法；空列表或读取失败有明确提示。
- [ ] 后端不会接受浏览器传来的任意仓库 URL、磁盘路径或 Git 参数。
- [ ] 现有模型训练、数据集和结果功能不因本任务回归。
- [ ] 前端 `npm run build` 通过。
- [ ] 后端 `mvn -DskipTests compile` 通过；新增 Registry 相关测试通过。
- [ ] PR 明确写出：新增字段、兼容策略、未完成项和验证结果。

## 6. 交接给开发者 B 的内容

合并前或 PR 审查阶段，需要向开发者 B 提供：

1. 已确认的登记 YAML 字段和示例；
2. 算法状态的可用枚举及含义；
3. 方向 ID、引擎 ID、数据格式 ID 的固定列表；
4. 平台读取登记信息的 API 说明；
5. 任何影响 `algorithm.yaml` 的兼容性变更。

开发者 B 不需要等待页面美化完成，但必须以本任务的登记字段为准制作试点算法仓库。

## 7. 风险提示

- 平台登记不能替代 GitHub 仓库权限；它只能描述算法，不应暴露私有凭据。
- 当前项目内 `research/` 仍是旧机制，迁移期间必须保持兼容，不能一次删除。
- `feature/component-download` 的单仓库 sparse checkout 方案不是多仓库权限隔离方案，不应作为本任务的前置依赖。
