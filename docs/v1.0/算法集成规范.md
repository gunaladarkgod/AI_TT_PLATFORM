# 研究算法与改进包开发规范

本规范用于将新的检测算法、研究基线和改进包接入 AI_TT_PLATFORM。算法实现、清单、Runner 运行参数和前端界面必须同时维护。分支、Issue、PR 和发布流程请阅读 [GitHub 协作流程](GitHub协作流程.md)。完整字段参考见 [research/algorithm-schema.md](../../research/algorithm-schema.md)。

## 1. 协作与通用规则

- 算法开发使用 `algo_算法简称` 分支，例如 `algo_rtdetr`；PR 先合并到 `develop`，集成验证通过后再由 `develop` 合并到 `main`。
- 所有路径使用相对项目根目录的路径；不得写入个人电脑绝对路径。
- 输出放在 `artifacts/<算法类别>/`；研究基线任务固定为 `artifacts/research/{方向}/{基线}/`。不得提交数据集、权重、日志、虚拟环境和按任务生成的配置。
- 每个算法 PR 必须说明：Python/依赖版本、输入数据格式、训练命令、输出目录、日志位置、停止方式和最小验证结果。

### 1.1 三层边界

- **平台核心层**：统一 Runner、引擎适配接口、任务队列、日志和产物管理。MMDetection、官方 Ultralytics 与外部自定义命令的通用运行能力属于此层。
- **研究基线层**：`research/{方向}/{基线}/algorithm.yaml`。基线引用一个平台引擎，并定义版本、数据格式、入口、默认参数和必要源码。
- **改进层**：`research/{方向}/{基线}/improvements/{改进包}/algorithm.yaml`。改进包只能在父基线上叠加配置或模块，不能修改基线文件。

引擎不是基线：一个引擎可被多个方向、多个基线复用；基线也不是改进包：改进包必须声明 `parent` 并由平台与父基线一起解析。

### 1.2 新增或修改改进包

每个可运行改进包至少要同时完成：

1. 在 `improvements/{改进包}/algorithm.yaml` 声明 `parent`、与父基线一致的 `engine`/`engine_version`/`data_format`，以及 `stack`。
2. 将可公开调节的值写入 `parameters`；每个 `key` 在“基线 + 已选改进包”中必须唯一。
3. 新增模块源码时放在该包的 `src/`，并由对应引擎的配置或训练入口实际导入；只写 YAML 但没有源码或合并逻辑，不得标记为可运行。
4. 配置覆盖写入 `stack.override_paths`；同一次组合中两个改进包覆盖相同路径会被拒绝。
5. 用 `stack.requires` 声明前置改进包，用 `stack.conflicts` 声明互斥改进包，值均使用完整的改进包 ID。

平台会以 `stack.priority` 升序解析改进包，并在前端选择、后端保存和 Runner 启动前重复校验。不要把安全或兼容性只写在前端。

## 2. MMDetection 模板方式

当前原始模式固定使用 `engines/mmdet_run/mmdetection-3.0.0` 与 MMEngine `Config`。适用于 Faster R-CNN、DETR、DINO、YOLOv3 等已由 MMDet 实现的模型。

### 2.1 添加模板

1. 在 `engines/mmdet_run/myfiles/template/{rcnn|detr|yolo}/` 新增完整 Python 模板，例如 `detr/rt-detr.py`。
2. 在 `engines/mmdet_run/mmdet_runner_srv/mmdet_config_service.py` 的 `TEMPLATE_CATALOG` 登记：

```python
"RT-DETR": ("DETR", "detr/rt-detr.py"),
```

3. 模板必须能被 `mmengine.config.Config.fromfile()` 单独读取，并包含模型、COCO 数据集、训练策略、评估器与运行时配置。

模板仅放文件不会自动显示：前端模板列表来自 `TEMPLATE_CATALOG`，经 `GET /api/config/templates` 返回。任务配置将生成在：

```text
engines/mmdet_run/myfiles/modelcfg/{任务名称}/config.py
```

该文件是本机运行产物，不是公共模板。

### 2.2 新增前端参数

前端入口：`fronternd/src/views/trainTask/index.vue`。每增加一个页面字段，必须完成完整闭环：

1. 添加表单控件与适用模板的显示条件。
2. 将字段加入前端参数对象和提交载荷。
3. 在 `template_defaults()` 从模板的真实配置路径读取默认值，保证切换模板、编辑任务时能回填。
4. 在 `generate_config()` 的写入逻辑中写回同一配置路径。
5. 验证“创建任务、切换模板、编辑任务、读取生成配置”四个场景。

例如“主干网络名称”必须同时对应前端字段和 `model.backbone.type`；只显示、不写入，或只写入、不回填均不合格。

### 2.3 版本限制

- 仅保证与 MMDetection **3.0.0**、当前 Runner Python 环境和 MMEngine 配置语法兼容。
- 不直接复制 MMDetection 2.x 的 `data`、`runner`、`optimizer_config` 等旧式配置。
- 不假设新版 MMDetection 的模块已安装；新增依赖必须安装到 Runner 实际使用的 Python 环境。
- 自定义模块须使用 `custom_imports` 明确导入，源码随项目提交，不依赖开发机路径。

## 3. YOLO 的两种方式

### 3.1 MMDetection YOLO

例如现有 `engines/mmdet_run/myfiles/template/yolo/yolov3.py`。它使用 `runner_mode=original`，复用 MMDet 模板、默认值、`config.py` 读写和 COCO 数据集流程；限制与 MMDet 3.0.0 完全一致。

### 3.2 Ultralytics YOLO

Ultralytics 的版本约束放在 `engines/yolo_run/ultralytics_runner/requirements.txt`。平台只有一个统一 Runner：创建任务时保存该任务的 Python/Conda 路径、YOLO 数据 YAML、模型与训练参数；Runner 只做预检、调度、日志、停止和产物管理，不维护第二个 Ultralytics 服务或环境。

**Ultralytics 不支持平台 MMDet 配置文件写入。** 不调用 `/api/config/*`，不生成 `engines/mmdet_run/myfiles/modelcfg/{任务名称}/config.py`。`data.yaml`、模型 YAML 和参数由 Ultralytics 自身管理；前端保存任务 Python、基线、改进包和最终参数。当前官方 Ultralytics 基线固定要求 `ultralytics==8.4.115`。

Ultralytics 改进包的参数必须是该版本官方 `model.train()` 支持的关键字。Runner 会按所选基线和改进包声明的参数 key 建立白名单，未声明参数会拒绝启动，而不是静默忽略。

## 4. 其他模型类别

每个新模型类别在 `engines/` 下建立独立运行目录：

```text
engines/xxx_run/
├─ README.md
├─ requirements.txt
├─ tools/train.py
└─ templates/        # 可选，供算法自身读取
```

前端选择“自定义”类别，使用固定 Runner 模式并保存：

| 参数 | 含义 | 示例 |
| --- | --- | --- |
| `fixed_python_path` | 训练解释器 | `.conda/envs/xxx/python.exe` |
| `fixed_exec_dir` | 执行目录 | `engines/xxx_run` |
| `fixed_command_line` | 训练命令 | `tools/train.py --run-id {run_id} --work-dir {work_dir}` |
| `fixed_work_root` | 输出根目录 | `artifacts/xxx` |

训练脚本须持续向标准输出写入 epoch、loss、mAP 与完成/失败信息，Runner 才能保存到 `train.log` 并让前端读取。自定义算法不使用 MMDet 的 `config.py`；结果查询中没有配置快照是正常现象，应在前端说明，而不是伪造 MMDet 配置。

## 5. Runner 接口约定

Runner 地址为 `http://127.0.0.1:8009`，新算法优先复用以下接口：

| 接口 | 用途 | 要求 |
| --- | --- | --- |
| `POST /api/runner/train?runId=...` | 启动训练 | 统一 Runner 接口。MMDet 用 `runner_mode=original`；外部自定义算法用 `runner_mode=fixed` 与四个 `fixed_*` 参数；Ultralytics 使用任务指定的 Python、`data_format=yolo`、基线/改进包解析后的 `ultralytics_parameters`。|
| `POST /api/runner/stop?runId=...` | 停止训练 | 不得绕过 Runner 另行后台启动训练进程。|
| `GET /api/runner/log/latest?runId=...` | 读取训练日志 | 脚本必须输出可读训练进度。|
| `GET /health` | 健康检查 | 集成与发布前必须检查。|

仅 MMDet 模板可使用配置接口：`GET /api/config/templates`、`GET /api/config/template/defaults`、`POST /api/config/generate`、`GET /api/config/read`。Ultralytics 和其他自定义算法不得伪装为 MMDet 配置调用这些接口。

结果查询中的“查看日志”和“打开路径”依赖 Runner 的目录定位接口。新增算法时必须让 `fixed_work_root` 位于项目 `artifacts/` 下，并完成 Runner 已启动、日志可读、结果目录可定位三项验证；Runner 不可用时，前端应返回“请先检查模型训练中 Runner 是否正常启动”的明确指引。

## 6. PR 验收清单

- [ ] 使用 `algo_算法简称` 分支，PR 目标为 `develop`。
- [ ] 所有路径为相对路径，未提交数据、权重、日志或本机环境。
- [ ] MMDet 模板已登记、可读取默认值、可生成 `config.py`，并在 3.0.0 环境验证。
- [ ] Ultralytics/自定义算法未误用 MMDet 配置读写。
- [ ] 基线/改进包的 `algorithm.yaml` 已通过目录校验；改进包的依赖、冲突、覆盖路径和参数 key 已验证。
- [ ] 若声明为可运行改进，已验证新增模块或参数确实进入训练命令，不能只验证界面显示。
- [ ] 已验证创建、发布、查看日志、停止训练和结果读取。
- [ ] PR 已记录依赖版本、命令、数据格式、输出位置和验证结果。
