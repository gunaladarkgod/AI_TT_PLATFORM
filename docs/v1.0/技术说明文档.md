# AI 训练平台技术说明文档

## 1. 架构与进程

| 模块 | 目录 | 默认端口 | 职责 |
| --- | --- | --- | --- |
| 前端 | `fronternd` | 5173（开发） | Vue 3 + Vite + Element Plus 管理界面 |
| 后端 | `backend` | 8081 | Spring Boot、MyBatis-Plus、数据集与任务 API |
| 数据库 | MySQL | 3306 | 用户、数据集登记、任务、训练结果等持久化数据 |
| 缓存 | Redis（可选） | 6379 | JWT 与临时缓存；可内存降级 |
| 统一 Runner | `engines/mmdet_run/mmdet_runner_srv` | 8009 | FastAPI 调度 MMDet、官方 Ultralytics、外部自定义命令；负责训练、停止、日志、产物定位与 MMDet 配置服务 |

开发模式下，Vite 将前端 `/develop/*` 代理到 `http://127.0.0.1:8081/*`。后端再通过 `sys.runner.train-url`（默认 `http://127.0.0.1:8009/api/runner/train`）调用 Python Runner。

## 2. 关键目录与路径策略

项目统一通过 `WorkspacePathUtil` 推导实际项目根目录，避免把某台电脑的绝对路径写进业务代码。

| 路径 | 说明 |
| --- | --- |
| `data/original_dataset` | 原始数据集的登记与辅助内容；外部导入的图片可在任意位置 |
| `data/instance_dataset_mid/{任务名称}` | 标签映射导出的中间实例数据集，COCO 标注，无训测划分 |
| `data/instance_dataset/{任务名称}/{实例数据集名称}` | 预处理完成的最终实例数据集 |
| `data/preprocess_scripts` | 上传的预处理/增强脚本 |
| `engines/mmdet_run/myfiles/template` | 内置 MMDet 模板源文件 |
| `engines/mmdet_run/myfiles/modelcfg/{任务名称}/config.py` | 任务保存时生成的最终训练配置 |
| `artifacts/mmdet_runs` | MMDet 训练的日志、权重和结果文件 |
| `artifacts/custom` | 固定 Runner/自定义算法训练的日志和结果文件 |
| `artifacts/research/{方向}/{基线}` | 研究基线任务（含改进包）的日志、权重、运行规格与结果文件 |
| `research/{方向}/{基线}/algorithm.yaml` | 基线的引擎、版本、数据格式、训练入口和参数声明 |
| `research/{方向}/{基线}/improvements/{改进包}/algorithm.yaml` | 改进包的父基线、叠加顺序、依赖、冲突、覆盖路径与参数声明 |
| `artifacts/result_metadata/{结果ID}.json` | 结果名称、备注、标签、产物目录和配置快照信息 |
| `logs/main/main.log` | 当前后端主日志 |
| `logs/history/` | 按日期归档的历史后端主日志 |

`APP_WORKSPACE_ROOT` 可显式指定项目根目录；未设置时，后端会从启动目录和代码位置向上搜索同时包含 `backend`，以及 `fronternd` 或 `engines/mmdet_run` 的目录。

## 3. 配置与启动维护

主要配置文件：[backend/src/main/resources/application.yml](../../backend/src/main/resources/application.yml)。

| 配置项/环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SERVER_PORT` | `8081` | 后端 HTTP 端口 |
| `DB_URL` | 本地 `ai_zm_master` | MySQL 连接串 |
| `DB_USERNAME` / `DB_PASSWORD` | `root` / `123456` | MySQL 账号 |
| `APP_FLYWAY_ENABLED` | `false` | 首次建库或升级时设为 `true` |
| `APP_FLYWAY_MODE` | `migrate` | 可用 `migrate`、`repair`、`disable` |
| `APP_REDIS_REQUIRED` | `true` | 无 Redis 时设为 `false`，避免启动等待 |
| `APP_REDIS_FALLBACK_MEMORY` | `false` | 无 Redis 时设为 `true`，启用内存缓存降级 |
| `RUNNER_AUTO_START` | `true` | 后端启动时自动拉起 Runner |
| `RUNNER_PYTHON` | 自动探测 | Runner 使用的 `python.exe` |
| `MMDET_REPO_ROOT` | 项目内 mmdetection | MMDetection 仓库路径 |
| `MMDET_WORK_ROOT` | `artifacts/mmdet_runs` | Runner 工作目录 |

数据库迁移脚本位于 `backend/src/main/resources/db/migration`，按 Flyway 版本号顺序执行。生产数据上不要执行 clean；项目配置已将 `clean-disabled` 固定为 `true`。

## 4. 数据集处理逻辑

原始数据集导入采用“登记外部路径”方式，不复制大量图片。预览、标签读取、导出时从登记路径读取真实图片和标注，因此外部路径失效会导致业务功能失效，但不会影响已生成的中间实例数据集和实例数据集。

`TaskDatasetDevController` 负责任务数据集管理。导出时依据映射规则筛选来源标注，合并同一任务类别，并生成标准 COCO 标注。输出固定为 `data/instance_dataset_mid/{任务名称}/images` 与 `annotations/instances.json`。

预处理输入只能是中间实例数据集；输出为最终实例数据集。每次创建生成独立子目录，避免覆盖历史预处理结果。创建时先按训练集占比随机划分原始图片及标注到 train/test，再分别执行增强或增广，避免同一原图及其增广副本跨训测集泄漏。实例数据集页面仍可使用重新划分接口调整已有数据集的训测比例。

## 5. 主要接口

| 分组 | 前缀 | 代表接口 |
| --- | --- | --- |
| 原始数据集 | `/original-dataset` | `GET /external`、`POST /external/import`、`POST /sample-random` |
| 任务数据集 | `/taskDatasetDev` | `POST /tasks`、`POST /tasks/mapping`、`POST /tasks/export`、`POST /tasks/clear`、`GET /tasks/preview` |
| 中间实例数据集 | `/instance-mid` | `GET /sourcedatasets` |
| 实例数据集 | `/instance` | `POST /instancedatasets`、`POST /instancedatasets/splitTrainTest`、`POST /instancedatasets/open-path` |
| 训练任务 | `/trainTask` | `POST /add`、`POST /update`、`POST /enqueue`、`POST /stop`、`POST /runner/log/latest` |
| Runner 管理 | `/api/runner` | `POST /health`、`POST /start`、`POST /dependencies/check` |
| 研究算法目录 | `/api/research` | `GET /directions`、`GET /baselines`、`GET /improvements`、`POST /stack/resolve` |
| 项目文档 | `/api/documentation` | `GET /usage-guide` |

新增接口时，应在对应 Controller 中定义清晰请求/响应结构，在 `fronternd/src/api/api.js` 中集中封装调用方法。涉及文件路径时，只允许服务端按 ID 或固定名称推导路径，不直接信任客户端的任意路径；删除文件前应确认目标在许可的数据根目录内。

## 6. 统一 Runner 与研究改进包

Windows 启动脚本为 `engines/mmdet_run/mmdet_runner_srv/start_runner.cmd`，Linux/macOS 使用 `start_runner.sh`。目录名因历史兼容保留 `mmdet_run`，Runner 本身是统一调度器，不代表只能运行 MMDet。

| Runner 接口 | 说明 |
| --- | --- |
| `GET /health` | 健康检查与活动训练状态 |
| `GET /api/config/templates` | 返回项目内模板目录中的可用模板 |
| `GET /api/config/template/defaults` | 读取模板默认配置值 |
| `POST /api/config/generate` | 基于模板生成任务 `config.py` |
| `GET /api/config/read` | 读取已生成任务配置 |
| `POST /api/runner/train` | 启动训练 |
| `POST /api/runner/stop` | 停止训练进程 |
| `GET /api/runner/log/latest` | 读取最新训练日志 |
| `POST /api/runner/result/delete` | 删除 Runner 本地结果 |
| `POST /api/runner/result/open` | 按结果名称、完成时间和输出根目录定位结果目录 |

运行分流规则：

- `engine=mmdet`：读取任务生成的 `config.py`，使用任务保存的训练 Python。
- `engine=ultralytics`：使用任务保存的 Python、YOLO `data.yaml`、模型和最终参数；当前要求 `ultralytics==8.4.115`。
- `engine=custom`：使用 fixed 模式的 Python、执行目录、命令行和输出根目录。
- `engine=paper`：保留引擎标识，但尚未接入论文源码训练，不可运行。

研究改进包在任务保存时通过 `POST /api/research/stack/resolve` 解析。后端同时校验父子关系、引擎/版本/数据格式一致性、依赖、冲突、覆盖路径和参数 key；保存后的声明参数列表会传给 Runner。Runner 拒绝未被所选基线或改进包声明的 Ultralytics 参数，避免浏览器请求注入任意训练选项。

模型类别和模板选项由前端内置回退、后端内置默认项及 `engines/mmdet_run/myfiles/template` 的实际文件共同决定，不依赖 `train_script`、`profile_train` 等数据库表中的模板记录。数据库仍保存训练任务、运行状态、备注和结果记录。

每次成功生成 MMDet 结果时，后端会把该任务生成的 `config.py` 复制到对应结果目录，并在 `artifacts/result_metadata` 保存其位置；结果查询中的“查看配置”读取这份快照，而非当前任务可能已被修改的配置。Ultralytics 任务会在运行目录保存 `ultralytics_run.json`，其中记录模型、数据、最终参数和改进包；固定 Runner/自定义任务本身不使用 MMDet `config.py`，没有配置快照属于正常情况。

## 7. 故障排查

### 后端无法启动

1. 检查 MySQL 服务、账号、密码和 `ai_zm_master` 数据库。
2. 首次启动缺表时启用 `APP_FLYWAY_ENABLED=true` 和 `APP_FLYWAY_MODE=migrate`。
3. 未安装 Redis 时设置 `APP_REDIS_REQUIRED=false;APP_REDIS_FALLBACK_MEMORY=true`。

### Runner 不可用

1. 在模型训练页面点击“刷新/启动”，查看返回的失败原因。
2. 手动执行 `start_runner.cmd`，确认 Python 路径和 FastAPI、Uvicorn、MMEngine 依赖。
3. 访问 `http://127.0.0.1:8009/health`，确认端口没有被其他程序占用。
4. 查看 `engines/mmdet_run/logs` 下的 Runner 日志。修改 Runner Python 代码后，需要由运行人员自行重启 Runner；修改后端 Controller 后，需要由运行人员自行重启后端。

结果查询的“查看日志”和“打开路径”需要 Runner 运行，因为 Runner 负责安全定位实际产物目录。Runner 未运行时，前端会提示先检查模型训练页中的 Runner 状态；“查看配置”不依赖 Runner，但历史结果或自定义任务可能没有 `config.py` 快照。

### 数据集预览没有图片或标注

1. 原始数据集：确认登记路径仍存在，并包含图片和对应标注。
2. 任务管理：确认中间实例数据集存在于 `data/instance_dataset_mid/{任务名称}`，且有 `images` 和 `annotations/instances.json`。
3. 实例数据集：确认目录位于 `data/instance_dataset/{任务名称}/{实例数据集名称}`；训测划分后图片可能位于 `images/train`、`images/test`。
4. 从后端日志定位请求接口、解析的目录、图片目录和 COCO 标注文件是否存在。

## 8. 维护约定

### 当前前端角色与个人中心

- `GET /auth/profile` 与 `GET /auth/users/roles` 在前端明确使用 `responseType=json`；公共请求方法默认的 `text` 会使返回的 JSON 成为字符串，页面读取 `code/data` 会失败。个人中心与登录资料刷新均复用这两个 JSON 查询。

- 用户权限管理入口按当前账号等级显示，不依赖个人资料加载成功；资料与权限列表失败分别提示。认证失败时重新登录，接口不存在时重启更新后的后端。入口可见不代表服务端授权成功，所有权限修改仍由后端校验。

- 本轮沿用现有账号类型：`1. 平台管理员`、`2. 基线维护者`、`3. 实验操作员`、`4. 改进开发者`。旧普通用户保留编号 3，新增`4. 改进开发者`使用编号 4；不自动重分配已有账号，不需要数据库结构迁移。
- 所有权限等级名称统一以“编号. 中文名称”显示：`1. 平台管理员`、`2. 基线维护者`、`3. 实验操作员`、`4. 改进开发者`。编号对应现有账号类型，仅调整显示文字，不改变数据库中的等级值和权限边界。
- 前端重点区分`4. 改进开发者`与`3. 实验操作员`。`4. 改进开发者`保留原有数据集准备、预处理、标签映射、训测划分、训练与结果维护功能；`3. 实验操作员`可以查询和预览数据集、创建和运行训练任务、调整已有允许参数以及查看结果，不能导入、修改、删除数据集、维护脚本、重新划分或维护结果。
- `3. 实验操作员`的维护入口隐藏，数据页面显示只读说明；旧维护页面通过菜单与路由限制，维护请求在前端统一拦截。此控制不替代后端接口鉴权，也不限制直接访问 Runner。数据、训练等原有后端接口的授权模型未全面重构；用户等级修改已在后端限制为`1. 平台管理员`。
- 平台核心、引擎适配、基线定义、改进包定义和源码修改继续通过 GitHub 权限及 PR 审查管理，本轮不新增这些编辑功能。
- 点击顶部用户头像或下拉菜单“个人中心”，可以查看账号、中文权限等级、权限说明，并完善人员姓名、研究方向、手机号与个人简介。复用 `sys_user.nickname/part/phone/remark`；新增 `GET/POST /auth/profile`，按服务端验证的登录凭据识别本人，保存入口只接受这四个资料字段，不能修改角色、状态、账号或密码。
- 界面与文档统一使用四种中文权限名称；英文标识仅保留为内部兼容代码，不在个人中心展示。
- 研究方向复用 `sys_user.part`，仅是个人资料，不用于范围授权；原字段内容原样保留，可由用户自行更新。
- 新增 `GET /auth/users/roles` 和 `POST /auth/users/role`：服务端验证登录凭据，并读取数据库中的当前状态与等级，仅`1. 平台管理员`可列出用户及修改其他用户等级。只接受固定等级 1～4，禁止修改自己的等级；成功变更后撤销目标用户全部登录凭据，要求重新登录。
- 原 `/user/update` 不再接受等级变更，避免绕过专用入口；`/user/add` 仅允许`1. 平台管理员`创建固定等级账号。用户资料和权限修改使用独立入口。
- 登录时读取最新个人资料；等级变更后用户需重新登录以更新菜单。角色授权尚未覆盖所有数据接口或直接访问 Runner。

### 通用维护规则

- 后续平台权限固定为四个角色：`1. 平台管理员`（用户管理、平台核心、Runner 与引擎适配）、`2. 基线维护者`（基线定义、源码和默认参数）、`4. 改进开发者`（改进包、模块源码和参数）、`3. 实验操作员`（创建任务、调整允许参数和查看结果）。不设计研究方向或基线范围授权，也不允许用户拥有临时自定义角色。当前前端已区分操作权限，用户等级管理已执行管理员鉴权，其他后端接口尚未全面强制执行该模型；后续应在现有用户类型、菜单权限和接口鉴权基础上扩展，并保留 GitHub 作为源码修改的审查入口。
- 不提交运行产物、大型数据集、模型权重和本地日志到代码仓库。
- 增加模板时，同时补齐模板文件、后端模板映射、Runner 模板目录和前端展示项；没有实际模板文件的选项应保持不可选。
- 新增研究基线或改进包时，先更新 `research/` 下的清单与说明，再实现对应模块源码或参数合并器；只有完整可运行的组合才能在训练界面开放选择。
- 修改路径规则时，优先修改 `WorkspacePathUtil`，不要在业务代码中新增用户电脑绝对路径。
- 数据库结构变更通过新的 Flyway 脚本完成，不修改已在其他环境执行过的历史迁移文件。
- 删除接口应明确“只删记录”还是“记录与本地文件都删”，并在前端进行二次确认。
- 新增顶级目录、运行产物目录或日志路径时，同步更新根目录 `README.md`、`.gitignore` 与 [GitHub 协作流程](GitHub协作流程.md) 的项目结构说明。
