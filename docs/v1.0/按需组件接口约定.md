# 按需组件接口约定

> 本文包含三套不同接口。`/api/workspace/components` 是历史的**平台仓库内**选择性下载；`/api/baseline-components` 管理外部 **B 基线仓库**；`/api/algorithm-components` 管理外部 **C 独立算法仓库**。前端不得将三者混用。

## 外部 B 基线组件接口（新接口，供基线管理与验证页面使用）

该接口只读取 `research-registry/algorithms/*.yaml` 中 `kind: baseline` 且 `source.type: external-git` 的登记。下载目标固定为 `local-components/baselines/<方向>/<基线>/`。B 是可独立验证、可作为 C 派生来源的代码起点；它不是已下载 C 的运行时依赖，也不会因下载、更新或删除 B 而修改 C。

当前阶段只完成 B 的“登记、受控下载、清单校验、验证资料”能力。统一 Runner 尚未执行 B 的通用训练入口，因此页面只能显示“可进入后续基线验证”的状态，不能伪装为已经完成训练。

### `GET /api/baseline-components?direction=<方向>`

需登录。返回 `data.components`、`data.registryErrors` 和最近一次 `data.task`。`direction` 可选；存在 `running` 组件任务时每两秒轮询，任务结束后停止。组件字段与 C 接口基本一致，但具有以下 B 专用语义：

| 字段 | 含义 |
| --- | --- |
| `kind` | 固定为 `baseline`。 |
| `localStatus` | `not-downloaded`、`downloaded`、`invalid`。 |
| `baselineValidationReady` | 仅当 B 已下载、清单匹配且登记为 `published` 时才可能为 `true`。它表示可进入后续基线验证流程，不表示已经完成训练。 |
| `trainingReady` | 对 B 固定为 `false`；B 不进入 C 的正式算法训练选择下拉框。 |
| `blockers` | 未下载、清单缺失/不一致、未发布等具体原因，必须原样显示。 |

### `GET /api/baseline-components/validation-profile?id=<登记ID>`

需登录。基线管理页选中 B 后调用。返回引擎、格式、清单相对路径、本机提交、`baselineValidationReady`、`blockers` 和 `runnerIntegration`。当前 `runnerIntegration=not-connected` 是明确的阶段阻塞，前端不得自行拼接命令启动训练。

### `POST /api/baseline-components/install` 与 `POST /api/baseline-components/remove`

仅平台管理员可调用；请求体均只有登记 ID：

```json
{"id":"small-object/yolo11-baseline"}
```

下载与移除的安全规则与 C 相同：服务端只使用登记中的仓库地址、版本和相对清单路径；不接受浏览器传入 URL、ref、路径、凭据或命令；删除前拒绝含已修改或未跟踪文件的本机副本。后台任务通过 GET 返回的 `data.task` 轮询，状态为 `running|succeeded|failed`。下载、更新与移除 B 都不会修改任何 C、平台源码、数据集、环境或训练结果。

### 前端边界

1. 新增“基线管理/基线验证”区域，B 与 C 分组展示，不能放进同一个“可训练算法”下拉框。
2. 平台管理员可见下载、移除操作；其他角色只读查看状态和原因。
3. 当 `baselineValidationReady=false` 时，显示 `blockers`；不得把“已下载”显示成“已验证”。
4. B 的基线验证结果后续应与 C 的正式实验结果分开归档；本接口不创建训练任务、不写训练产物。

## 独立 C 算法组件接口（新接口，供多仓库前端页面使用）

该接口读取平台仓库中 `research-registry/algorithms/*.yaml` 的 `external-git` 登记，只允许服务端用已登记的仓库地址、分支/Tag 和相对清单路径操作。下载目标固定为被 `.gitignore` 忽略的 `local-components/algorithms/<方向>/<算法>/`；不改动平台的 Git 工作区，也不下载 B 基线仓库。

当前实现只覆盖“列出、受控下载、受控移除、训练选择资料”。统一 Runner 对 C 的**真实执行**仍须等 C 补齐标准清单和入口后单独接入；前端不能把此接口当作任意命令执行器。

### `GET /api/algorithm-components?direction=<方向>`

需登录。返回 `data.components`、`data.registryErrors` 和最近一次 `data.task`。`direction` 可选；页面在组件任务 `running` 时每两秒轮询，任务结束后停止。

每项字段：

| 字段 | 含义 |
| --- | --- |
| `id` / `name` / `direction` | 平台登记的稳定标识与显示信息。 |
| `registrationStatus` | `draft`、`review`、`published` 等登记成熟度，不等于本机已存在。 |
| `engine` / `dataFormat` | 登记的引擎及版本、数据格式。 |
| `localStatus` | `not-downloaded`、`downloaded`、`invalid`。 |
| `trainingReady` | 仅当本机清单匹配且已发布时才可能为 `true`。前端只允许该状态进入训练任务创建选择。 |
| `blockers` | 不可下载、清单缺失/不一致、未发布等具体原因，必须原样可见。 |
| `sourceCommit` | 已下载 C 的本机 HEAD；未下载或无法读取时为 `null`。 |
| `derivedFrom` | C 对 B 的来源记录，仅供展示和追溯。 |
| `installAllowed` / `removeAllowed` | 当前操作是否可能由管理员发起；仍以服务端权限校验为准。 |

### `GET /api/algorithm-components/training-profile?id=<登记ID>`

需登录。训练页在用户选择一个已下载 C 后调用。返回登记 ID、引擎、格式、清单相对路径、本机状态、`trainingReady`、`blockers`、本机提交版本和 `runnerIntegration`。

当前 `runnerIntegration=not-connected` 表示尚未将 C 的受控训练入口接进统一 Runner；它是明确的阶段性阻塞，不是前端故障。不得据此构造路径或命令请求 Runner。

### `POST /api/algorithm-components/install`

仅平台管理员可调用。请求体只有登记 ID：

```json
{"id":"small-object/tdsc"}
```

服务端在临时目录执行非交互 Git 克隆，之后移动到固定本机组件目录并校验 C 的 `algorithm.yaml`、`derived-from.yaml` 及其训练入口。请求不接受 URL、Git ref、目标路径、Token 或 Shell 参数。成功只表示后台任务已创建；通过 GET 返回的 `data.task.status` 判断最终状态。状态为 `running|succeeded|failed`，并附带 `message`、`logs`、`algorithmId`、`operation` 与时间信息。下载失败不会暴露原始 Git 错误或凭据。

### `POST /api/algorithm-components/remove`

仅平台管理员可调用，请求体同下载。服务端会先检查目标是 Git 仓库且工作区没有已修改或未跟踪文件；不满足时拒绝删除，不覆盖或清理开发者本地修改。移除只影响本机 `local-components` 下的 C 副本，不删除 GitHub 上的 C/B 仓库、平台源码、数据集、环境或训练结果。

### 前端行为与安全边界

1. 管理员看到下载/移除按钮，其他用户只读查看状态；服务端仍会重复校验角色。
2. `not-downloaded`、`invalid`、`trainingReady=false` 只能显示状态和原因，不能出现在“可训练算法”下拉框中。
3. 页面只能保存/传递登记 `id`；不得保存或显示服务器绝对路径、Git 凭据或 Git 命令。
4. B 页面使用 `/api/baseline-components`，C 页面使用 `/api/algorithm-components`；旧训练引擎/研究目录按需下载仍使用下方旧接口，直到独立迁移完成。

## 平台内旧组件接口（历史 sparse checkout）

模型训练页的“组件管理”由后端检测并直接下载引擎和研究方向，写入后端所在机器的当前项目工作区。不安装 Python 依赖、不下载权重、不更新或切换分支。

## 使用

需要使用 Git cone 模式选择性克隆，并由平台管理员点击下载。完整克隆不会自动转为 sparse；ZIP 下载不支持补充下载。后端需要 Git、工作区写权限和已有仓库访问凭据，后台不弹出认证窗口。

选择研究方向对应的引擎，点击“下载”或“补充下载”。方向下载同时补充对应引擎，只检出该引擎的基线及其目录内改进包，保留原来的 sparse 选择。界面每两秒轮询，显示阶段日志和完成/失败状态，不估算下载百分比。

下载完成后自动刷新组件状态。关闭弹窗后重新打开训练表单或刷新训练页以加载研究目录，再通过已有入口检查训练 Python 环境。文件齐全不代表环境可训练，也不表示研究草稿已实现。

目标组件含本地修改或未跟踪文件时拒绝下载。失败保留已有文件和 sparse 选择，可检查并重试。关闭弹窗不取消任务，重新打开可查看当前进程最近一次任务；后端重启后任务记录不保留，文件重新检测。

### 删除组件

已下载或不完整的组件显示“删除组件”，由平台管理员确认后执行。研究方向只删除当前所选引擎的基线和目录内改进包，保留引擎与另一引擎的基线。仍有研究方向基线依赖某引擎时，必须先删除该引擎对应的方向组件，再删除引擎。

删除通过调整 sparse 选择移除源码，保留平台、其他组件、Git 对象、独立 Python 环境、数据集和训练结果。目标内有修改、未跟踪文件或被忽略的环境/缓存/运行文件时拒绝删除；请先保存、移走这些文件。完整克隆不自动转换，不强制删除文件。组件被 `engines` 或 `research` 等更大的 sparse 选择包含时，提示手动细分选择。

删除前先停止使用该组件的训练任务。删除成功可再次下载，适合反复验证组件流程；此操作不卸载 Python 包，也不释放 `.git` 中已缓存对象占用的空间。

## 接口

`GET /api/workspace/components?engine=ultralytics`

需要登录。`engine` 为 `ultralytics`（默认）或 `mmdet`，决定方向组件的基线集合。成功响应使用 `AjaxResult`，`code=0`，`data` 为 `{ "components": [...], "downloadSupported": true, "message": "", "task": {} }`。`message` 说明不能下载的原因。每个组件包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 稳定组件 ID，例如 `mmdet`、`ultralytics`、`small-object`、`knowledge-distillation` |
| `kind` | string | `engine` 或 `direction` |
| `name` | string | 前端显示名称 |
| `status` | string | `ready` 关键文件齐全、`missing` 未检出目录、`partial` 缺少关键文件 |
| `path` 或 `relativePath` | string | 相对项目根目录的组件路径 |
| `engine` | string | 当前选择的方向引擎 |
| `message` | string | 可选的状态详情或缺失项说明 |

### POST /api/workspace/components/download

需要平台管理员身份，读取数据库中的当前角色。请求为 JSON：

```json
{"id":"small-object","engine":"ultralytics"}
```

成功返回任务快照：`id`、`componentId`、`engine`、`status`、`message`、`logs`。状态为 `running|succeeded|failed`。轮询 GET 接口的 `data.task` 查询最新快照。同一后端进程同时只允许一个下载任务。

### POST /api/workspace/components/remove

请求体与下载相同，需要平台管理员。返回同样的后台任务快照；新增 `operation=download|remove` 区分操作，下载和删除共用串行任务锁。通过 GET 的 `data.task` 查询阶段日志和结果。删除时使用 `git sparse-checkout set --cone -- ...`，根据当前完整 sparse 清单仅移除目标选择，保留其余选择；存在无法安全解释的特殊路径时拒绝自动修改。

服务端组件清单在 `WorkspaceComponentService`，即使组件未下载也可以展示；新增基线时同步维护。当前检查固定关键文件存在性，不解析全部算法引用，不检查 Python 包；Runner 在线情况另行检测。MMDet 引擎可用性也会检查关键文件，避免仅 Runner 在线就误报可用。

所有路径来自服务端固定清单。不接受客户端命令、远程地址或路径；使用参数数组执行 `git sparse-checkout add -- ...`，不用 Shell，不 reset/restore、不切分支、不改全局 Git 配置。单次补充操作超时十分钟。失败提示不返回可能包含凭据的原始 Git 输出。

下载按当前分支目录树补充，partial clone 按需获取缺失对象，不执行 fetch/pull。私有仓库需要后端系统账号已有 SSH 密钥或 HTTPS 凭据。一个工作区只运行一个后端实例，下载期间避免并发手动 Git 操作或编辑目标组件文件。

## 验证

后端：`mvn -Dtest=WorkspaceComponentServiceTest,WorkspaceComponentControllerTest test`，使用临时本地 Git 仓库验证按引擎隔离、保留已有选择、本地修改保护、无 Git/完整克隆处理及匿名访问限制，无需远程仓库和数据库。

前端：在 `fronternd` 运行 `npm run build`。真实私有远程下载仍依赖部署机器 Git 凭据和网络。

Git 文件状态仅解析标准输出；尚未检出目录导致的标准错误警告不视为本地修改。回归测试覆盖仅存在 MMDet 运行目录、Ultralytics 父目录尚不存在时的引擎单独下载。
