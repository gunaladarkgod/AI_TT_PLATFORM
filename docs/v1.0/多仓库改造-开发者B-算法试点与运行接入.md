# 多仓库改造任务书 B：算法试点、运行接入与可复现工作区

**负责人：** 开发者 B（算法与运行接入方向）

**建议分支：** `feature/external-algorithm-pilot`

**PR 目标：** `develop`
**前置条件：** 从最新 `develop` 创建分支；与开发者 A 确认本任务第 3 节的登记字段后开始实现。

## 1. 任务目标

验证“平台核心仓库 A + 独立算法仓库 C”的最小可行链路。第一阶段只选择一个方案：

```text
小目标检测 / 官方 Ultralytics / YOLO11 基线
```

目标不是一次迁移全部算法，而是让该方案能以独立仓库保存自己的配置、源码、入口和依赖说明，并被平台以受控方式识别、校验、调度和记录版本。

## 2. 范围与边界

### 2.1 本任务必须完成

1. 制定独立算法仓库模板，至少包含：

   ```text
   AI_TT_ALGO_SMALL_OBJECT_YOLO11_BASELINE/
   ├─ algorithm.yaml
   ├─ README.md
   ├─ configs/
   ├─ src/
   ├─ scripts/
   ├─ requirements/
   ├─ tests/
   └─ examples/
   ```

2. 编写并验证 `algorithm.yaml`，其字段必须与开发者 A 的算法登记协议兼容。
3. 为 YOLO11 小目标基线形成一个真实、最小、可复现的训练入口：使用任务保存的 Python、YOLO `data.yaml`、平台统一 Runner 和 `ultralytics==8.4.115`。
4. 平台需要以**固定且受控的算法根目录**读取试点算法清单；不得信任前端传递的任意绝对路径、训练脚本或仓库地址。
5. 训练结果必须记录平台提交、算法仓库提交、算法 ID、引擎版本、数据格式、最终参数及配置快照/运行规格。
6. 提供一个可复现工作区方案，用 Git 子模块或等价的受版本控制清单固定：平台版本 + 该试点算法版本。该工作区只用于组合，不承载业务源码。

### 2.2 本任务明确不做

- 不迁移 MMDetection、DETR、知识蒸馏或论文源码。
- 不实现“多个改进包任意动态叠加”的源码组合；这属于后续独立阶段。
- 不由后端自动克隆、拉取、切换、删除任意外部 Git 仓库。
- 不改变开发者 A 负责的研究基线公约页面、登记目录结构和展示 API。
- 不修改数据集预处理的 COCO/YOLO 导出逻辑。
- 不启动、关闭或重启后端、Runner。

## 3. 与开发者 A 的固定协议

试点算法在平台登记中使用以下最小信息：

```yaml
id: small-object/yolo11-baseline
direction: small-object
status: draft
repository:
  url: https://github.com/<organization>/AI_TT_ALGO_SMALL_OBJECT_YOLO11_BASELINE.git
  default_ref: develop
  stable_ref: null
platform:
  min_version: null
engine:
  id: ultralytics
  version: 8.4.115
data_format: yolo
algorithm_manifest: algorithm.yaml
```

算法仓库根目录的 `algorithm.yaml` 至少包含：

```yaml
schema_version: 1
id: small-object/yolo11-baseline
name: YOLO11 小目标检测基线
kind: baseline
engine: ultralytics
engine_version: 8.4.115
data_format: yolo
entry: scripts/train.py
default_config: configs/default.yaml
parameters: []
```

两份清单中的 `id`、`engine`、`engine_version`、`data_format` 必须一致。发现不一致时，平台必须拒绝启动，并解释是哪一个字段不匹配。

## 4. 推荐实现方式

### 4.1 算法源码接入目录

当前阶段建议由平台管理员在本地以固定目录接入已审核的算法仓库，例如：

```text
components/
└─ small-object/
   └─ yolo11-baseline/
```

该目录应加入 `.gitignore`，不把外部算法源码重复提交进平台仓库。平台后端只按“登记 ID -> 固定组件根目录”的映射推导路径，不能接受浏览器传来的路径。

正式多方案使用时，可建立单独的工作区仓库：

```text
AI_TT_WORKSPACE_SMALL_OBJECT/
├─ platform/                         # AI_TT_PLATFORM 子模块
├─ algorithms/yolo11-baseline/        # 算法仓库子模块
└─ workspace-lock.yaml                # 可选：记录组合、版本与用途
```

不要让每个算法仓库嵌入一份完整的平台副本；多个算法需要在同一平台实例下比较时，应由工作区仓库统一组合平台和算法仓库。

### 4.2 Runner 接入原则

- Runner 仍由 `AI_TT_PLATFORM/runner/` 提供，算法仓库不能自行启动第二个 Runner。
- 使用 `engine=ultralytics`，且仅接收 YOLO 格式实例数据集和已声明的参数白名单。
- Python/Conda 环境由创建训练任务时保存；算法仓库只声明依赖和兼容版本，不覆盖用户选择的 Python。
- Runner 启动前必须分别检查：算法清单、算法入口、引擎文件、Runner 健康状态、Python 依赖、YOLO `data.yaml`、数据格式。
- 任何检查失败都应返回明确不可用原因，不能把“文件存在”误报为“可以训练”。

### 4.3 结果可复现性

每次试点训练的产物目录或结果元数据至少保存：

- 平台 Git 提交或 Release Tag；
- 算法仓库 URL、提交 ID 或 Release Tag；
- 算法 ID 和 `algorithm.yaml` 快照；
- 引擎 ID、引擎版本和训练 Python；
- 实例数据集 ID、数据格式及 `data.yaml` 相对路径；
- 最终训练参数、实际训练命令和输出相对目录。

不得保存 Git 凭据、私人绝对路径、数据集副本、权重副本或虚拟环境文件到源码仓库。

## 5. 阶段性目标与完成程度

每个阶段结束时都应提交一个可审查的本地提交。任何阶段未达到完成标志时，都应如实记录阻塞原因，不能用“目录已建立”代替运行验证。

### 阶段 B0：试点协议与仓库骨架

**要做什么：** 阅读项目根目录 `README.md`、技术说明、GitHub 协作流程、算法集成规范及开发者 A 提供的登记协议；建立 YOLO11 试点算法仓库模板和最小 `algorithm.yaml`。

**完成标志：** 算法仓库的目录职责明确，`algorithm.yaml` 能通过静态字段校验，并与开发者 A 的登记中 `id`、引擎、版本、数据格式一致。

**尚未完成时不能声称：** 创建空仓库、复制 README 或写出占位训练脚本，不等于算法方案已经接入平台。

### 阶段 B1：最小训练入口

**要做什么：** 实现或整理一个 YOLO11 小目标基线训练入口，明确其配置、默认模型、参数、YOLO `data.yaml` 输入和输出目录；确认其复用现有 Ultralytics 运行方式。

**完成标志：** 不依赖个人绝对路径、不另起训练服务；从代码和文档上可以确定平台将用什么 Python、什么入口和什么相对输出目录运行它。

**尚未完成时不能声称：** 能调用 `ultralytics` 包不等于能够被统一 Runner 调度；不得新增第二个 Runner。

### 阶段 B2：受控算法接入与预检

**要做什么：** 在平台侧建立“登记 ID -> 固定组件根目录”的受控映射，读取算法 `algorithm.yaml` 并与平台登记交叉校验；补齐源码、入口、引擎、Runner、Python、数据格式、YOLO `data.yaml` 的分项预检。

**完成标志：** 前端或接口能准确区分“未接入源码”“源码不完整”“环境不可用”“Runner 未启动”“数据格式不匹配”和“可尝试训练”；客户端不能传入任意路径、脚本或 Git URL。

**尚未完成时不能声称：** 仅发现目录存在或清单可读，不得显示为“可训练”。

### 阶段 B3：运行规格与一次端到端验证

**要做什么：** 将平台提交、算法提交、算法清单、引擎/环境、数据格式、最终参数及输出目录写入结果运行规格；在干净环境完成一次真实训练验证。

**完成标志：** 能从一条结果记录追溯到准确的平台版本、算法版本和参数；训练可启动、日志可读取、结果可定位。若真实训练被环境或数据阻塞，至少应完成到失败前的全部预检，并记录可复现的阻塞原因。

**尚未完成时不能声称：** 仅能创建训练任务、仅有结果目录或仅有模拟日志，都不能标记为稳定接入。

### 阶段 B4：可复现工作区

**要做什么：** 建立单算法的工作区组合示例，固定平台与算法版本，并写清首次克隆、子模块初始化、版本更新和回退方式。

**完成标志：** 新成员按文档可取得“一个平台版本 + 一个算法版本”的同一组合；工作区不提交平台副本、算法副本、数据、权重、日志或本机环境。

**尚未完成时不能声称：** 多个仓库分别能克隆，不等于某次实验组合已可复现。

## 6. 验收标准

- [ ] 算法仓库可脱离平台主仓库独立维护，未复制平台源码、数据、权重和日志。
- [ ] 平台能通过登记 ID 找到受控算法根目录并读取 `algorithm.yaml`。
- [ ] 发现缺少源码、入口、YOLO `data.yaml`、Runner、Python 依赖或版本不匹配时，均有明确错误提示。
- [ ] Ultralytics 训练仍复用统一 Runner，不产生第二套 Runner 或固定 Python 环境。
- [ ] 结果元数据包含平台与算法的可复现版本信息。
- [ ] 不影响现有本地 `research/` 方案和既有训练任务的使用。
- [ ] 后端编译、相关测试、前端构建通过。
- [ ] PR 中包含真实验证结论；未进行真实训练时不得描述为已稳定接入。

## 7. 交接给开发者 A 的内容

完成试点后，需要向开发者 A 反馈：

1. 最终确认的 `algorithm.yaml` 字段、样例和校验规则；
2. 算法登记中必须新增或调整的字段；
3. 平台展示“未接入”“源码存在”“环境可用”“可训练”四种状态所需信息；
4. 工作区组合方式及固定版本格式；
5. 已验证项、未验证项及其阻塞原因。

## 8. 风险提示

- 独立仓库不等于任意仓库都可被平台执行。平台只能运行管理员登记、目录固定、清单通过校验的方案。
- GitHub 仓库权限控制源码读取；平台四级用户角色控制平台功能。两者必须分别维护。
- 当前改进包的“组合规则”主要是协议和目录校验，尚未形成跨仓库源码插件系统。不要在本任务中承诺任意改进包可叠加训练。
